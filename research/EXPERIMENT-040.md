# App Split VPN 0.4.0: промежуточный эксперимент

Ветка `experiment/multi-vpn-0.4.0`. Рабочая ветка, APT-индексы, DEB-файлы,
GitHub Releases и `ios.ratu.sh` не изменяются. На iPhone установлен исходный 0.3.0.
Исходники в этой ветке пока **не являются готовым 0.4.0**; версия пакета ещё не повышена.

## Интерфейс

- BYPASS показывает DIRECT; TUNNEL ONLY — VPN; MULTI VPN — VPN MATRIX.
- Скрытые списки не удаляются. В статусе показывается только релевантный список.
- VPN MATRIX содержит назначения `bundleID -> configuration UUID`.
- Группировка/фильтрация по VPN-профилю доступны только в VPN MATRIX.
- Однопрофильные Extra пока скрыты в MULTI VPN; его отдельный контроллер не готов.
  Сохранённые однопрофильные опции не исполняются в MULTI, включая при выключенном
  переключателе разделения. Резервирование предусмотрено **только** для BYPASS/TUNNEL ONLY.
- Тюнинг скрыт, пока не включены LS или Health Check. Задержка появляется только
  для LS; метод/ресурс/порт/интервал/таймаут/порог — только для Health Check;
  порт скрыт для PING. Список резервов и алгоритм появляются при резервировании.
- Состояние Extra появляется после включения опции. Журнал остаётся доступным
  после автоматической остановки опций, чтобы причина остановки была видна.
- «PiP / музыка не отключают VPN на LS» — выключенная по умолчанию зависимая
  опция в Тюнинге, видна только при включённом LS. Состояние воспроизведения
  запрашивается через `MRMediaRemoteGetNowPlayingApplicationIsPlaying` в фоне,
  не чаще одного раза в 2 секунды и только при нужных настройках и блокировке.
  Пауза запускает обычную задержку LS; неизвестное/устаревшее состояние сохраняет
  VPN. После блокировки и включения защиты обязательно запрашивается свежий результат.
  RU/EN и подсказки добавлены. Полная проверка отключения/удержания ещё не выполнена.
- Профили резервов: поиск, группы/фильтры по владельцу-приложению, алфавиту,
  выбранному состоянию; отдельные сортировки групп и профилей; номера выбора.

## Защита от циклов

`RecoveryCore.h` разделяет счётчик неудачных проверок и неудачных циклов
восстановления. Успешная проверка обнуляет серию неудачных циклов. Round-Robin
и Random выбирают только ещё не проверенные резервы в текущем неуспешном круге.
Переносимое тестирование: `cc -Wall -Wextra -Werror research/recovery-test.c`.
Интеграционные проверки supervisor на телефоне ещё не выполнены.

## Проверенные механизмы телефона

iPhone15,3, iOS 17.0, Dopamine 3.0.10, ElleKit 1.2.

1. `NEConfigurationManager` перечисляет сохранённые профили, включая выключенные.
2. Для временного преобразования обычного профиля в per-app требуется
   `NEVPNApp` с копией протокола, его исходным `tunnelType = 1`, правилами
   `NEAppRule` и `noRestriction`. Значение по умолчанию `tunnelType = 2`
   ошибочно запрашивало AppProxy-провайдер вместо PacketTunnel.
3. `NETunnelProviderManager.forPerAppVPN`, привязка конфигурации и обязательная
   `loadFromPreferencesWithCompletionHandler:` позволяют запустить per-app сеанс.
   Низкоуровневый `ne_session_create` использует тип 2, вместо типа 1 для обычного VPN.
4. SWE-via-RU-3.1 awg (Default VPN) и DE (rat-hole) (WireGuard) одновременно
   сохраняли статус Connected на протяжении 40-секундных проверок.
5. Интерфейс определяется через точный UUID **протокола**, а не UUID конфигурации,
   в `SCDynamicStore` `State:/Network/Service/<protocol UUID>/IPv4` / `IPv6`.
6. Root-сеанс `NEPolicySession` принимает правила по UUID исполняемых файлов.
   Это **не подтверждает работоспособность передачи данных**.

## Что пока не доказано

Запросы CLI curl/wget при `tunnelIPToInterfaceName:secondaryResultType:0`
не проходят. Попытка socket scope дала таймаут одного запроса и ответ другого,
но независимость путей не подтверждена. Вариант `realApplication:` дал прямой IP
провайдера — это не успех туннелирования. Независимый выходной IP приложений
и правильная обработка их DNS ещё требуют подтверждения.
Нужно отдельно проверить совместные сеансы одного провайдера и остальные VPN-приложения.

### Проверки 2 октября 2026

- Без изменения framing на обоих per-app utun подтверждён флаг
  `UTUN_FLAGS_ENABLE_PROC_UUID` (4). XNU добавляет 16 байт UUID к обычным
  4 байтам адресного семейства. Raw-fd WireGuard ожидает обычные 4 байта.
  В захвате встречались входящие пакеты с отсутствующими первыми 16 байтами
  IPv4-заголовка. Это не доказательство рабочего обмена данными.
- Контрольный **обычный** WireGuard DE выполнил числовые HTTPS-запросы curl/wget:
  `104.28.197.9`, DE. Сам профиль и сервер работоспособны в этом режиме.
- Флаг устанавливается в `NEHelperSocketFactory handleMessage:` процесса nehelper.
  Отправитель — nesessionmanager. Его синхронный запрос находится внутри
  `NESMVPNSession plugin:didRequestVirtualInterfaceWithParameters:completionHandler:`,
  где можно проверить точный UUID принадлежащего эксперименту appVPN.
- Ограниченный Frida-прототип меняет только такой запрос, сохраняя остальные
  socket options; исходный XPC объект восстанавливается после синхронного вызова.
  NetworkExtension повторно устанавливает FLAGS после получения подключённого FD.
  Ядро отказывает даже для уже установленного значения; прототип считает это
  успешным no-op **только после getsockopt, подтверждающего требуемое значение**.
  Без этого VPN падает с NEVPNConnectionErrorDomain 12.
- После этой коррекции оба профиля снова Connected, на SWE видны корректные
  входящие IPv4/TCP пакеты. На DE в одном тесте повторялись DNS-запросы без
  подтверждённых ответов. Числовые CLI-запросы через отдельные NECP IP_TUNNEL
  по-прежнему не прошли. MULTI пока **не подтверждён** и не включён в демон.
- Следующий тест с `realApplication:` для физических исключений **провайдера**,
  вместо `effectiveApplication:`, подтвердил числовой HTTPS из процесса myIP:
  `APP_EGRESS com.monvpn.myip = 104.28.197.9, DE`, при обоих per-app сеансах
  Connected и отключённых обычных сеансах. WireGuard engine handle 0 имел
  handshake, TX/RX и endpoint. Raw utun FLAGS=0 подтверждён отдельно.
  Штатный запрос runtime-статистики через NETunnelProviderSession при этом
  вернул пустые данные, хотя сам engine работал: пустой ответ не равен отсутствию engine.
  На SWE захвачены двусторонние корректные TCP пакеты. Видимый IP WhatIsMyIP
  и повторяемость обоих путей ещё проверяются. Исторический неудачный результат
  не переписывается как успех: найден и отдельно проверен новый вариант.
- Matrix-прототип теперь использует `realApplication:` только для провайдеров,
  а выбранным приложениям разрешает штатные per-app правила через SKIP.
  На недоступный назначенный профиль остаётся DROP. Это пока не интегрировано
  в рабочий демон и не делает весь эксперимент готовым продуктом.
- По указанию пользователя тестовые приложения заменены на
  WhatIsMyIP (`mobi.secured.whatsmyip`) и myIP (`com.monvpn.myip`). Telegram
  не используется как индикатор доступности, особенно на выходах с российским IP.
- Standalone root CLI получил `MEDIA_PLAYING=0` без медиа, `1` при Яндекс Музыке
  и `1` при сообщённом пользователем PiP VK Видео. Дополнительно SpringBoard
  подтвердил `isUILocked=true` и `isPlaying=true` одновременно. Обычный `lockstate`
  в одном замере возвращал 0, позднее — 1. Поэтому добавлен отдельный read-only
  `LockState.x`, фильтр только SpringBoard, передающий `isUILocked` демону через
  свою Darwin-notification. ABI `_reallySetUILocked:` проверен: void / BOOL.
  Ограниченный Frida-прототип подтвердил передачу из SpringBoard в root CLI:
  `UI_LOCK_VALID=1 UI_LOCKED=1 MEDIA_PLAYING=1`; также увидел снятие UI-блокировки.
  Внедрение собранного модуля и фактическое удержание VPN новой версией ещё не проверены.
  Новая опция на телефон пока не установлена; там по-прежнему 0.3.0.

Исходники для проверки framing:
[if_utun.h](https://github.com/apple-oss-distributions/xnu/blob/xnu-10002.1.13/bsd/net/if_utun.h),
[if_utun.c](https://github.com/apple-oss-distributions/xnu/blob/xnu-10002.1.13/bsd/net/if_utun.c),
[WireGuard Darwin TUN](https://github.com/WireGuard/wireguard-go/blob/master/tun/tun_darwin.go).

Поэтому основной демон явно отвергает MULTI VPN как ещё не проверенный режим,
а не подменяет его BYPASS. Прототип matrix-политик пока не включён в рабочий цикл.

Исходники Apple для разбора NECP:
[necp.h](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/net/necp.h),
[necp.c для Darwin 23](https://github.com/apple-oss-distributions/xnu/blob/xnu-10002.1.13/bsd/net/necp.c).

## Безопасность эксперимента

Дополнительный тест с перестановкой назначений подтвердил
`APP_EGRESS com.monvpn.myip = 77.110.97.12, FI` при назначении SWE;
до перестановки тот же процесс выходил через DE (104.28.197.9).
Оба per-app сеанса оставались Connected, обычные сеансы были отключены.
Видимый результат второго приложения WhatIsMyIP пока не подтверждён.
После завершения восстановлены оригинальные профили и supervisor;
обычный HTTPS с телефона снова показал 77.110.97.12, FI.

Framing-прототип перенесён в отдельный `MultiPacketCompat.x`, строго
для nesessionmanager и root-owned manifest выбранных UUID. Без manifest
модуль ничего не меняет. Предварительная WSL-компиляция прошла; на телефон
модуль не установлен, транзакционный MULTI backend ещё не интегрирован.

`run-multi-traffic.sh` сначала штатно отключает старые split-правила, затем
приостанавливает supervisor и запускает ограниченный по времени отдельный CLI.
EXIT/HUP/INT/TERM восстанавливают исходные конфигурации и переключатель разделения.
Конфигурации резервируются только на телефоне в файле с правами 0600. Этот файл
может содержать чувствительные сведения; его нельзя копировать в Git или логи.
Повторный тест отказывается перезаписывать резервную копию уже преобразованным профилем.

WSL-компиляция — только предварительная проверка. Пакет с внедрением в системные
процессы нельзя устанавливать из WSL: окончательная сборка требует macOS/Xcode
и проверки arm64e PTRAUTH. Ни установка нового пакета, ни CI-релиз пока не выполнялись.
